# Remediation H1: Calibration Loop Can't Close (Downstream Attribution is Impractical)

## 1. Finding Summary
**H1: Calibration Loop Can't Close — Downstream Attribution is Impractical.**
The verdict ledger currently mandates recording `downstream_outcome` to calculate a true cost-per-defect metric. However, automatically attributing post-deployment bugs to specific agentic validator verdicts generated weeks earlier is functionally impossible in fast-moving repositories. As a result, the calibration loop remains perpetually open, and the cost-per-defect metric is purely aspirational.

## 2. Root Cause
The calibration design in `calibration_and_measurement.md` relied on a closed-loop feedback mechanism extending all the way to post-deployment (production). Given the system's architecture (23 agents, 8-phase pipeline) and the reality of fast-moving git histories, tracing a production bug back to a specific `GateResult` generated by a validator is intractably complex without massive manual intervention. The original design over-indexed on ideal metrics (true defect cost) rather than observable, near-term proxy metrics, which broke the automated Shadow Mode promotion mechanics.

## 3. Detailed Remediation

The remediation abandons mandatory downstream attribution in favor of near-term, highly observable proxy metrics: Human Agreement Rate (Tier 1) and Integration-Time Catch Rate (Tier 2).

### 3.1. Restructuring Calibration Metrics into Tiers
We redefine calibration and measurement into three distinct tiers based on observability:

*   **Tier 1: Human Agreement Rate (Immediate):** The frequency with which the validator's verdict matches a human reviewer's explicit override or approval on the PR/diff. This is 100% observable.
*   **Tier 2: Integration-Time Catch Rate (Near-Term):** The rate at which integration testing (e.g., test harness runs, staging deployments, post-merge CI) catches a defect that the validator *approved*. This is highly observable as it occurs within hours/days of the verdict.
*   **Tier 3: Downstream Outcome (Aspirational/Optional):** Manual or highly heuristic-driven attribution of production bugs. This is no longer on the critical path for agent promotion.

### 3.2. Pydantic Schema Updates (`agent_interface_contracts.py`)
The `VerdictLedgerEntry` schema must be updated to reflect the new tiered reality. We will change `downstream_outcome` to an optional field and introduce `integration_catch_outcome`.

```python
from pydantic import BaseModel, ConfigDict, Field
from typing import Optional

class VerdictLedgerEntry(BaseModel):
    model_config = ConfigDict(frozen=True, extra="forbid")

    gate_result: str = Field(..., description="The original agentic GateResult (e.g., 'pass', 'fail')")
    reviewer_spec_version: str = Field(..., description="Version of the prompts/rules used")
    human_override: Optional[str] = Field(None, description="Tier 1: Explicit human verdict overriding or confirming the agent")
    integration_catch_outcome: Optional[bool] = Field(None, description="Tier 2: True if integration tests caught an issue on the approved code within the CI window")
    downstream_outcome: Optional[str] = Field(None, description="Tier 3: Optional manual notation of a production bug attributed to this verdict")
```

### 3.3. Shadow Mode Promotion Thresholds
Given the small team size (1 architect + 2-3 devs), we cannot rely on vast statistical significance. We need pragmatic thresholds.
To promote an agent from Shadow Mode to Active Blocking Mode, it must meet the following criteria over a rolling window of **N = 50** executions:
*   **Tier 1 (Precision against human review):** $\ge 95\%$ agreement rate with human overrides/approvals.
*   **Tier 2 (Integration catch rate on agent approvals):** $\le 5\%$ false positive approval rate (integration tests catch a defect the agent approved in fewer than 5% of cases).

### 3.4. Cost-Per-Defect Reformulation
We abandon "Cost-per-production-defect." Instead, we measure **Cost-per-Integration-Catch (CPIC)** and **Cost-per-Verdict**.
*   **Cost-per-Verdict:** Total inference spend (using dispatch-path metering as per `budget_and_escalation_policy.md §4.3`) divided by total evaluations.
*   **Cost-per-Integration-Catch:** Total inference spend of the validator divided by the number of legitimate defects it caught before integration.
This targets the \$5-50/run constraint by ensuring the cost of running the agent is strictly bounded and justified by the immediate defects it prevents from entering the integration branch.

## 4. Required Plan Document Updates

*   **`calibration_and_measurement.md`**:
    *   Rewrite §2 to define Tier 1, Tier 2, and Tier 3 metrics.
    *   Update the `VerdictLedgerEntry` schema definition.
    *   Establish the N=50 run threshold and 95% Tier 1 / 5% Tier 2 criteria for Shadow Mode promotion.
    *   Deprecate the automated closed-loop production requirement.
*   **`budget_and_escalation_policy.md`**:
    *   Update §4 to replace `Cost-per-production-defect` with `Cost-per-Integration-Catch`.
    *   Ensure dispatch-path metering explicitly tags costs to the `VerdictLedgerEntry` ID for accurate Cost-per-Verdict calculation.
*   **`agent_interface_contracts.py`**:
    *   Apply the Pydantic schema changes defined in Section 3.2.

## 5. New Open Questions

*   **CI Window Definition:** How long do we wait for a Tier 2 "Integration-Time Catch" before officially sealing the ledger entry? (e.g., 48 hours post-merge, or purely based on the immediate post-merge CI pipeline success?)
*   **Heuristic for Tier 2 Attribution:** If an integration test fails, how do we programmatically confirm it was a defect the *agent* should have caught, versus a flake or an unrelated integration issue? (Likely requires a simple heuristic: if the modified files overlap with the failing test suite, count it as a potential miss).
